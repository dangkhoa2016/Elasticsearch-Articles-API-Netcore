# C# Scripting Guide: Installation, Usage, and Internal Mechanics of `dotnet-script`

This guide provides a comprehensive walkthrough on how to manage `dotnet-script` as a local tool, execute standalone C# files without a traditional `.csproj` project, and understand what happens behind the scenes during execution.

---

## 1. Managing `dotnet-script` Installation

Managing `dotnet-script` as a **Local Tool** using a tool manifest file (`dotnet-tools.json`) is the most reliable approach for isolated environments or specific cloud shell sessions.

### Install `dotnet-script`

To install or ensure `dotnet-script` is up-to-date in your current directory manifest, run:

```bash
dotnet tool install dotnet-script

```

*Output expectation:*

```text
Tool 'dotnet-script' (version '2.0.0') was successfully installed. Entry is added to the manifest file [your home directory]/dotnet-tools.json.

```

### Uninstall `dotnet-script`

If you ever need to remove the tool from your manifest, use the following command:

```bash
dotnet tool uninstall dotnet-script

```

*Output expectation:*

```text
Tool 'dotnet-script' was successfully uninstalled and removed from manifest file [your home directory]/dotnet-tools.json.

```

## 2. Preparing Your C# Script File

Unlike standard C# Console Applications, `dotnet-script` natively supports **Top-level statements** and inline NuGet package references using the `#r "nuget:..."` directive.

Create a file named `test.cs` inside `[your workspace folder]` and paste the following code:

```csharp
#r "nuget: Newtonsoft.Json, 13.0.4"
using Newtonsoft.Json;

Console.WriteLine("Hello World");

// Create an anonymous object
var product = new { Name = "Apple", ExpiryDate = new DateTime(2008, 12, 28) };

// Serialize the object to a JSON string
string json = JsonConvert.SerializeObject(product);
Console.WriteLine(json);

```

> 💡 **Note:** The `#r` directive automatically pulls the `Newtonsoft.Json` package (version 13.0.4) from the NuGet registry on the fly if it is not already cached in your local environment.

---

## 3. Running the Script

Since `dotnet-script` is installed as a local tool within your manifest, you can invoke it using either of the following commands from your terminal:

### Option A: Using `dotnet tool run` (Standard)

```bash
dotnet tool run dotnet-script [your workspace folder]/test.cs

```

### Option B: Using `dotnet dotnet-script` (Shorthand)

```bash
dotnet dotnet-script [your workspace folder]/test.cs

```

### Option C: Using `dotnet script` (Shorthand)

```bash
dotnet script [your workspace folder]/test.cs

```

### Expected Output

Upon execution, the script outputs the results directly to your terminal screen:

```text
Hello World
{"Name":"Apple","ExpiryDate":"2008-12-28T00:00:00"}

```

## 4. Under the Hood: The Cache Folder Structure

When you execute `test.cs`, `dotnet-script` does not just evaluate code strictly in memory. To handle external dependencies seamlessly, it dynamically spins up a shadow project structure inside the system's `.cache` directory.

Below is the directory tree generated automatically under `[your home directory]/.cache/dotnet-script/`:

```text
[your home directory]/.cache/dotnet-script/[full path of the running script]/
├── net10.0/
│   ├── script.csproj                 <-- Temp project file generated by dotnet-script
│   ├── script.csproj.cache
│   └── obj/                          <-- Contains NuGet configuration files for restoration
│       ├── project.assets.json       <-- Dependency mapping graph (includes Newtonsoft.Json)
│       ├── project.nuget.cache
│       ├── script.csproj.nuget.dgspec.json
│       ├── script.csproj.nuget.g.props
│       └── script.csproj.nuget.g.targets
└── test.cs/
    └── execution-cache/              <-- Execution cache zone (compiled artifacts)
        ├── script.dll                <-- The actual compiled binary of your test.cs file
        ├── script.sha256             <-- SHA256 hash used to track script modifications
        ├── Newtonsoft.Json.dll       <-- Local copy of the third-party library dependency
        └── obj/
            ├── project.assets.json
            └── script.csproj.nuget.g.props

```

### How the Execution Mechanism Works:

1. **Shadow Project Generation (`net10.0/script.csproj`)**: `dotnet-script` extracts information from your script file (such as the targeted .NET framework and the `#r "nuget:..."` directives) to assemble a standard `.csproj` file. This tricks the .NET SDK into treating your single script file like a formal application.
2. **Implicit Dependency Restore (`obj/project.assets.json`)**: It executes an implicit `dotnet restore`. The presence of `project.assets.json` confirms that the tool has successfully mapped and retrieved `Newtonsoft.Json` from either your local environment cache or the remote NuGet registry.
3. **Execution Caching (`execution-cache/`)**: To ensure blazing-fast execution speeds on subsequent runs, `dotnet-script` saves the compiled script as `script.dll` along with a `script.sha256` checksum file.
* **First Run:** Takes a few moments to restore dependencies and generate this cache structure.
* **Subsequent Runs:** `dotnet-script` compares the current hash of your `test.cs` file with the saved `script.sha256`. If the code has not changed, it completely skips the compilation phase and **runs the `script.dll` directly**, executing almost instantly.
